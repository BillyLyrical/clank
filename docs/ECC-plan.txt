## 1. Continuous Learning / Instincts

**ECC source**: /home/clam/ref/ECC/skills/continuous-learning-v2/

**What it does**: Hooks capture tool-use observations → background observer
(Haiku, cheap model) detects patterns → creates atomic "instincts" with
confidence scores → instincts cluster into skills/commands/agents.

**Key files**:
- /home/clam/ref/ECC/skills/continuous-learning-v2/SKILL.md — pipeline spec
- Hooks on PreToolUse and PostToolUse capture observations
- Project scoping: instincts scoped to git-remote-hash, promote to global
  at confidence >= 0.8 after 2+ projects
- Confidence decay: -0.02/week without observation, -0.1 per contradiction

**Clank adaptation**:
Extend Crystallizer with confidence-weighted ephemeral rules:
- Add `confidence` (0.0-1.0) and `last_observed` timestamp to crystallized_rules
- Add decay: confidence -= 0.02/week when unused, -= 0.1 on contradiction
- Add project scoping: hash of git remote URL as scope key
- Promotion: rules with confidence >= 0.8 seen in 2+ scopes become global
- Display: `/stats` shows automation ratio + confidence distribution

**Effort**: Medium (extend Crystallizer schema + add decay/promotion logic)

## 2. GateGuard: Force Investigation Before Editing

**ECC source**: /home/clam/ref/ECC/skills/gateguard/

**What it does**: PreToolUse hook that forces the agent to investigate
before editing files. Three stages:
1. DENY — block first edit attempt
2. FORCE — demand specific facts: importers, schemas, user instruction
3. ALLOW — permit retry with gathered context

Measured +2.25 quality points vs ungated.

**Key file**: /home/clam/ref/ECC/skills/gateguard/SKILL.md

**Clank adaptation**:
Wire as a bus hook on `pre_tool_use` events for write/edit tools:
- First edit attempt: block, return "investigate before editing"
- Inject instructions: "grep for importers of this module, read the schema,
  confirm the user's intent"
- Second attempt: allow

Could be a wit (`wits/guardrails/`) that subscribes to `pre_tool_use` and
blocks writes until the agent has gathered context.

**Effort**: Low (bus hook + pre_tool_use interception, existing patterns)

## 4. Agent/Skill/Hook Three-Layer Split

**ECC source**: /home/clam/ref/ECC/agents/*.md, /home/clam/ref/ECC/skills/*/SKILL.md

**What it does**: Clean separation of concerns:
- **Agents** = who does it (prompt + tool allowlist + model)
- **Skills** = what workflow (Markdown + optional scripts)
- **Hooks** = what triggers automatically (event-driven)

68 agents as plain Markdown files with YAML frontmatter. 286 skills.
94 legacy command shims being deprecated.

**Key files**:
- /home/clam/ref/ECC/agents/*.md — agent definitions (prompt + tools)
- /home/clam/ref/ECC/skills/*/SKILL.md — skill definitions
- /home/clam/ref/ECC/AGENTS.md — orchestrator routing

**Clank adaptation**:
Wits currently mix all three concerns. Consider:
- Agents: named prompt templates with tool allowlists (for subagent spawning)
- Skills: workflow definitions (what Clank already has as wits)
- Hooks: bus subscriptions (what wits already do, but formalize)

Not urgent — our wit system works. But for scaling to 200+ wits,
the separation helps humans navigate.

**Effort**: Low (documentation + convention, no code changes needed)

**Status**: ✅ Done — docs/ARCHITECTURE_LAYERS.md documents the three-layer
separation (agents=who, wits=what, hooks=when). Scaling threshold noted
at ~200 wits.

## 5. Council: Adversarial Decision-Making

**ECC source**: /home/clam/ref/ECC/skills/council/

**What it does**: Four-voice adversarial decision-making:
- Architect (constructive), Skeptic (critical), Pragmatist (practical),
  Critic (quality)
- Each sees only the question (anti-anchoring — no cross-contamination)
- Synthesized by a fifth agent

**Key file**: /home/clam/ref/ECC/skills/council/SKILL.md

**Clank adaptation**:
Implement as a "band" (bus workflow) or a subagent-spawning wit.
Spawn 4 parallel subagents with isolated prompts, collect results,
synthesize. Useful for ambiguous architectural decisions.

Clank's subagent system already supports this — just need the orchestration
wit that spawns 4 specialized prompts and merges results.

**Effort**: Low (wit that spawns 4 subagents via existing infrastructure)

## 6. Skill Compliance Testing

**ECC source**: /home/clam/ref/ECC/skills/skill-comply/

**What it does**: Meta-quality measurement. Auto-generates test scenarios
at 3 prompt strictness levels, runs agents, classifies tool call sequences,
reports compliance rates. Are agents actually following their declared skills?

**Key file**: /home/clam/ref/ECC/skills/skill-comply/SKILL.md

**Clank adaptation**:
Build a compliance test wit that:
- Reads wit metadata (hint, about, usage)
- Generates test prompts that should trigger specific wits
- Runs agent loop, checks which tools were called
- Reports: "wit X was expected 10 times, triggered 8 times (80% compliance)"

This is valuable for our 141 wits — are they actually being selected by RATS?

**Effort**: Medium (test generation + compliance scoring logic)

durable structured knowledge. Could add a `memory_documents` table with
kind/status/scope columns, queryable via FTS5.

Not urgent — WorldModel handles most cases. But "lesson" and "runbook"
kinds are interesting for cross-session learning.

**Effort**: Low-Medium (new table + bus topic, no changes to WorldModel)

**Status**: ✅ Done — lib/Clank/Memory.pm with memory_documents table
(ECC memory.v1 compatible), FTS5 search, CRUD, bus integration,
8 typed kinds (context/decision/fact/handoff/lesson/note/preference/runbook),
3 scopes (project/team/user), 3 statuses (active/rejected/superseded),

## 8. Dispatcher Fan-Out Pattern

**ECC source**: /home/clam/ref/ECC/skills/continuous-learning-v2/ (uses consolidated dispatchers)

**What it does**: Instead of N individual hook processes per event,
consolidated dispatchers (pre-bash-dispatcher.js, posttooluse-dispatcher.js)
fan out internally. Reduces process spawning.

**Clank adaptation**:
Our bus is in-process (synchronous dispatch), so this doesn't apply
directly. But the pattern matters if we add external hook processes:
one dispatcher per event type, fan out internally.

**Effort**: N/A for now (in-process bus handles this)

### Current Clank Bus Events (ad-hoc)
The bus has formalized topics: `context_knowledge_request`, `pre_tool_use`,
`post_tool_use`, `agent_end`, `turn_start`, `turn_end`, etc.

### ECC Hook Events (18 typed events)
From /home/clam/ref/ECC/schemas/hooks.schema.json:

| ECC Event | Clank Equivalent | Action |
|-----------|-----------------|--------|
| SessionStart | (none) | Add `session_start` topic |
| UserPromptSubmit | (none — Loop.pm handles) | Add `user_prompt_submit` topic |
| PreToolUse | `pre_tool_use` (renamed) | Done |
| PermissionRequest | (none) | Add `permission_request` topic |
| PostToolUse | `post_tool_use` (renamed) | Done |
| PostToolUseFailure | (none) | Add `tool_failure` topic |
| Notification | (none) | Add `notification` topic |
| SubagentStart | (none) | Add `subagent_start` topic |
| Stop | `agent_end` (exists) | Rename or alias |

| PreCompact | (none) | Add `pre_compact` topic |
| InstructionsLoaded | (none) | Add `instructions_loaded` topic |
| TeammateIdle | (none) | Not needed (single-agent) |

| WorktreeCreate | (none) | Add `worktree_create` topic |
| WorktreeRemove | (none) | Add `worktree_remove` topic |
| SessionEnd | (none) | Add `session_end` topic |

### Proposed Clank Bus Event Vocabulary

```
Session lifecycle:
  session_start          — session created or resumed
  session_end            — session closing

Prompt lifecycle:
  user_prompt_submit     — user input received (before agent processes)

Tool lifecycle:
  pre_tool_use           — before tool execution
  post_tool_use          — after tool success
  post_tool_use_failure  — after tool failure (NEW)
  permission_request     — tool requires permission (NEW)

Agent lifecycle:
  agent_start            — agent loop begins a turn
  agent_end              — agent loop finishes (existing)
  turn_start             — individual turn begins (existing)
  turn_end               — individual turn ends (existing)

Subagent lifecycle:
  subagent_start         — subagent spawned (NEW)
  subagent_stop          — subagent completed (NEW)

Context lifecycle:
  pre_compact            — before context compaction (NEW)
  post_compact           — after compaction (NEW)
  instructions_loaded    — system prompt assembled (NEW)

Task lifecycle:
  task_completed         — background task finished (NEW)

Config:
  config_change          — configuration modified (NEW)
```

### Implementation
- Add topic constants to `Clank::Bus` or a new `Clank::Bus::Topics`
- Emit new events from Loop.pm at appropriate points
- Rename existing topics with backward-compatible aliases
- Add profile gating: ContextRules DSL gains `profile => 'standard'`
  (minimal/standard/strict) to control which hooks fire
